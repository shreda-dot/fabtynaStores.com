# Fabtyna Stores — backend schema reference

Database: **PostgreSQL (Neon)**. Schema source: [`apps/api/prisma/schema.prisma`](../apps/api/prisma/schema.prisma).

> **The Prisma migration history is the single source of truth for the database.**
> There is no `prisma/sql-drafts/` folder any more. Every `CHECK`, partial unique
> index, trigger and function that Prisma cannot express was authored by hand
> and folded into a named migration under
> [`apps/api/prisma/migrations/**`](../apps/api/prisma/migrations). Changing the
> database means adding a migration, never editing a draft.
>
> **Never edit a migration that has already been applied to any database that
> matters.** Prisma records a checksum for each applied migration; editing the
> file afterwards makes the history diverge from the database. Fix mistakes with
> a **new** migration that drops/replaces the old object — never by rewriting an
> applied file and never by patching `_prisma_migrations` by hand.
>
> **Review every autogenerated migration before applying it.** `prisma migrate
dev --create-only` diffs the schema against the database, and Prisma cannot
> express the two hand-written, `DEFERRABLE` foreign keys between `expenses` and
> `loan_repayments` (migration `20261017000600`). It therefore emits
> `DROP CONSTRAINT` for `fk_expenses_loan_repayment` and
> `fk_loan_repayments_expense` in _every_ generated migration. Delete those
> two statements (and re-add the intended change). `db:verify` checks both
> foreign keys by name, so a dropped one fails loudly.

## 1. Conventions

| Convention         | Rule                                                                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Money              | Integer **kobo** in `BIGINT` (`BigInt` in Prisma). DTOs expose them as integer **strings**; `bigint` is only used for arithmetic.                                                 |
| Timestamps         | `timestamptz` (`DateTime`).                                                                                                                                                       |
| Business dates     | Lagos business dates are stored as `String` in `YYYY-MM-DD` form (produced by `getLagosBusinessDate()`), never as a `Date`, so they cannot shift by a timezone conversion.        |
| Table names        | `snake_case` via `@@map`.                                                                                                                                                         |
| Column names       | **camelCase** — Prisma maps table names only. Raw SQL must double-quote them (`"paidKobo"`).                                                                                      |
| Ledgers            | Append-only. A correction is a **new** row whose `reversesEntryId` points at the original.                                                                                        |
| Connection strings | Migrations/schema commands use `DIRECT_URL` (direct Neon host, no pooler) declared in `prisma.config.ts`. The runtime client uses pooled `DATABASE_URL` through a driver adapter. |

## 4. Constraints in plain English

### 4.1 Signed ledger amounts (`20261017000100`)

No ledger amount may be zero, and each entry type carries a fixed sign:

- **Customer ledger** — `SALE` positive; `PAYMENT`, `RETURN`, `CUSTOMER_REFUND` negative; `ADJUSTMENT` either sign.
- **Supplier ledger** — `PURCHASE` positive; `PAYMENT` negative; `ADJUSTMENT` either sign.
- **Account ledger** — `SALE_PAYMENT`, `CUSTOMER_PAYMENT`, `TRANSFER_IN`, `OWNER_CAPITAL`, `OTHER_INCOME` positive; `SUPPLIER_PAYMENT`, `EXPENSE`, `CUSTOMER_REFUND`, `TRANSFER_OUT`, `OWNER_DRAWING`, `BANK_OR_POS_CHARGE` negative; `ADJUSTMENT` either sign.
- **Loan ledger** — `DISBURSEMENT`, `CHARGE` positive; `REPAYMENT` negative.

### 4.2 Stock movements (`20261017000200`)

- Exactly one of `purchaseLineId`, `saleLineId`, `transferLegId`, `adjustmentLineId`, `returnLineId` is set.
- `PURCHASE` positive, `SALE` negative, `RETURN` positive; `ADJUSTMENT` and `TRANSFER` non-zero in either direction (a transfer's sign is checked against its leg by a trigger).
- `unitCostKobo >= 0`.

### 4.3 Partial unique indexes (`20261017000300`)

- `products.sku` is unique **among non-deleted rows** only, so a deleted SKU can be reused.
- For each ledger, at most **one live entry** (`reversesEntryId IS NULL`) exists per source document — one entry per sale, sale payment, purchase, supplier payment, expense, transfer, etc.
- A given row can be the target of **at most one reversal** (`ux_*_reversed_once`): you cannot reverse the same entry twice.

### 4.4 Value sanity (`20261017000500`)

- **products** — `unitsPerPack > 0`, all prices and the average cost `>= 0`, `reorderLevelUnits >= 0`, and a `sku` is stored upper-cased and trimmed.
- **customers** — `creditLimitKobo >= 0`.
- **purchases** — `totalKobo >= 0`, `paidKobo >= 0`, `paidKobo <= totalKobo`, `dueDate` matches `YYYY-MM-DD`.
- **purchase_lines** — `quantity > 0`, `unitsPerPackSnapshot > 0`, `quantityUnits > 0`, `PACK` lines have `quantityUnits = quantity * unitsPerPackSnapshot` and `UNIT` lines have `quantityUnits = quantity`, all money `>= 0`.
- **sales** — `totalKobo >= 0`, `paidKobo >= 0`, `paidKobo <= totalKobo`, and `channel <> 'BOTH'` (a sale is RETAIL or WHOLESALE; only a _product_ may be BOTH).
- **sale_lines** — as purchase lines, plus `unitPriceKobo`, `costPerUnitKobo`, `lineTotalKobo >= 0`.
- **stock_transfers** — `from <> to`; **stock_transfer_lines** — `quantityUnits > 0`.
- **stock_adjustment_lines** — `quantityDeltaUnits <> 0`, `unitCostKobo >= 0`.
- **sale_payments / supplier_payments** — `amountKobo > 0`.
- **expenses** — `amountKobo > 0`.
- **loans** — `principalKobo > 0`, `agreedInterestKobo >= 0`, `dueDate` matches `YYYY-MM-DD`.
- **loan_repayments** — `amountKobo > 0`, `interestPortionKobo >= 0`, `interestPortionKobo <= amountKobo`.
- **cash_snapshots** — `amountKobo >= 0`, `asOfDate` matches `YYYY-MM-DD`.

### 4.5 Accounting links (`20261017000600`)

- `loan_repayments.expenseId` and `expenses.loanRepaymentId` reference each other. Both keys are **`DEFERRABLE INITIALLY DEFERRED`** so the pair can be inserted in either order inside one transaction, and **`ON DELETE RESTRICT`** so neither side can be deleted while the other points at it.
- An expense that carries a `loanRepaymentId` **must** use category `LOAN_INTEREST`. The reverse is allowed: a manual `LOAN_INTEREST` expense may exist with no repayment.
- A `REPAYMENT` loan ledger entry **must** reference its `loanRepaymentId`; `DISBURSEMENT` and `CHARGE` entries **must not**.

### 4.6 Credit rules and the sale lifecycle (`20261017000700`)

- **Unpaid purchase requires a supplier** — if `paidKobo < totalKobo` then `supplierId IS NOT NULL`. Mirrors `createPurchase()`. A fully paid purchase (or a draft) needs no supplier.
- **Unpaid sale requires a customer** — if `paidKobo < totalKobo` then `customerId IS NOT NULL`. Mirrors `validateCompletedSalePayment()` and the UI, which refuses "a walk-in cannot owe money". `customerName` is deliberately **not** accepted as an alternative.
- **Sale status lifecycle** — `VOIDED` is terminal (no transition out of it) and a `COMPLETED` sale may never return to `DRAFT`. Legal transitions: `DRAFT → COMPLETED`, and any state `→ VOIDED`.

### 4.7 References

`sales.reference`, `purchases.reference` and `stock_transfers.reference` are unique. The columns are nullable, so **multiple NULLs are allowed** (Postgres treats NULLs as distinct in a unique index); a non-null reference can never be reused.

### 4.8 Admin users (`20261017051123`)

- **`email` is stored normalised** — `CHECK (email = lower(btrim(email)))`. The seed script normalises before writing; this CHECK is what enforces it against any writer.
- **`role` is not a security boundary.** `AdminRole` is `OWNER` or `STAFF` (default `STAFF`) and **nothing reads it yet** — there is no authorization layer, so every account has full access.
- **Accounts are deactivated, never deleted** (`isActive = false`): `purchases`, `sales`, `stock_transfers` and `stock_adjustments` reference `admin_users` with `ON DELETE RESTRICT`.
- **`lastLoginAt`** is nullable and stays null until sign-in exists. It is stored as `TIMESTAMPTZ(3)` (the documented convention above); note it is currently the only `timestamptz` column — every other timestamp column in the schema is `timestamp(3)`.

`20261017000400_immutability_triggers`

| Function                       | Trigger(s)                                                                                               | Effect                                                                                                                     |
| ------------------------------ | -------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `fn_raise_immutable()`         | `trg_<table>_immutable` on the 10 immutable tables                                                       | Raises on any `UPDATE` or `DELETE`.                                                                                        |

| `fn_check_transfer_leg_sign()` | `trg_stock_movement_transfer_leg_sign` on `stock_movements`                                              | An `OUT` transfer movement must be negative, an `IN` one positive, matching the leg's `direction`.                         |

## 6. Database-enforced vs service-owned

**Enforced by the database (cannot be bypassed by application code):**

- Immutability of the 10 ledger/payment/audit tables (including `TRUNCATE`).
- Reverse-once and no-reversal-of-a-reversal.
- Signed amounts for every ledger.
- Single-source stock movements, quantity signs, transfer-leg sign agreement.
- Every value-sanity rule in §4.4.
- Every foreign key, and `ON DELETE RESTRICT` on all of them (a referenced product, customer, supplier or sale cannot be hard-deleted).
- Unique references and the active-SKU rule.
- Unpaid purchase requires a supplier; unpaid sale requires a customer.
- `VOIDED` is terminal for a sale; `COMPLETED` never returns to `DRAFT`.
- Expense ↔ loan-repayment links and loan-ledger source exclusivity.
- `admin_users.email` is stored lower-cased and trimmed (`20261017051123`).

**Owned by the service layer (the database cannot express these):**

| Rule                                                         | Why it is service-owned                                                                                                                                                                    |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Stock never goes below zero                                  | A balance is the sum of immutable `stock_movements`; there is no balance row to constrain, so the check needs a row lock in a transaction (`apps/api/src/modules/stock/stock.service.ts`). |
| No duplicate balance row per `(product, location)`           | There is no balance table — balances are derived from the ledger by design.                                                                                                                |
| `lineTotalKobo` equals unit cost × quantity                  | Legitimate rounding can differ; the service computes the line total once and stores it.                                                                                                    |
| `paidKobo` equals the sum of the matching payment rows       | `paidKobo` is a denormalisation the payment service owns; the commented drift-audit query at the bottom of `20261017000500_value_checks` proves there is no gap.                           |
| A `PURCHASE`/`SALE` line quantity must result in whole units | Arithmetic and pack snapshots are resolved before the insert.                                                                                                                              |
| VOIDED sales/purchases/transfers must not be edited          | Immutability plus the status triggers cover most of it; the remaining "don't offer the action in the UI" checks live in the app.                                                           |
| Debtor aging / payment allocation to the oldest unpaid sale  | Computed at query time; there is no allocation table.                                                                                                                                      |

## 7. Drift audit

`paidKobo` is denormalised on `purchases` and `sales`. Run these two by hand (or via the constraint test suite) — **both must return zero rows on clean data**, then fix any row by writing the missing payment or reversing it:

```sql
SELECT p.id, p."paidKobo", COALESCE(SUM(sp."amountKobo"), 0) AS actual
  FROM purchases p
  LEFT JOIN supplier_payments sp ON sp."purchaseId" = p.id
  GROUP BY p.id, p."paidKobo"
  HAVING p."paidKobo" <> COALESCE(SUM(sp."amountKobo"), 0);

SELECT s.id, s."paidKobo", COALESCE(SUM(sp."amountKobo"), 0) AS actual
  FROM sales s
  LEFT JOIN sale_payments sp ON sp."saleId" = s.id
  GROUP BY s.id, s."paidKobo"
  HAVING s."paidKobo" <> COALESCE(SUM(sp."amountKobo"), 0);
```

> Known exception: a purchase with **no supplier** records no `supplier_payments`
> row at all (`SupplierPayment.supplierId` is NOT NULL), so a paid supplier-less
> purchase will appear in the first query. The domain layer sets
> `Purchase.paidKobo` regardless. This is a known gap, not drift.
