# Fabtyna Stores — backend schema reference

Database: **PostgreSQL (Neon)**. Schema source: [`apps/api/prisma/schema.prisma`](../apps/api/prisma/schema.prisma).

> **The Prisma migration history is the single source of truth for the database.**
> There is no `prisma/sql-drafts/` folder any more. Every `CHECK`, partial unique
> index, trigger and function that Prisma cannot express was authored by hand
> and folded into a named migration under
> [`apps/api/prisma/migrations/**`](../apps/api/prisma/migrations). Changing the
> database means adding a migration, never editing a draft.
>
> **Never edit a migration that has already been applied to any database that
> matters.** Prisma records a checksum for each applied migration; editing the
> file afterwards makes the history diverge from the database. Fix mistakes with
> a **new** migration that drops/replaces the old object — never by rewriting an
> applied file and never by patching `_prisma_migrations` by hand.
>
> **Review every autogenerated migration before applying it.** `prisma migrate
dev --create-only` diffs the schema against the database. The one surviving
> hand-written foreign key, `fk_expenses_loan_repayment` (installed by
> `20261017000600` as `DEFERRABLE INITIALLY DEFERRED`), is now also declared in
> `schema.prisma` through `@relation(..., map: "fk_expenses_loan_repayment")`,
> so Prisma recognises the name and no longer emits a `DROP CONSTRAINT` for it.
> Before STEP 1 the `expenses`/`loan_repayments` pair was _mutual_, and both
> halves were hand-written; migration `20261017060000` retired the reverse half
> (`LoanRepayment.expenseId`, `fk_loan_repayments_expense`). `db:verify` still
> checks `fk_expenses_loan_repayment` by name, so a dropped or renamed
> constraint fails loudly.

## 1. Conventions

| Convention         | Rule                                                                                                                                                                              |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Money              | Integer **kobo** in `BIGINT` (`BigInt` in Prisma). DTOs expose them as integer **strings**; `bigint` is only used for arithmetic.                                                 |
| Timestamps         | `timestamptz` (`DateTime`).                                                                                                                                                       |
| Business dates     | Lagos business dates are stored as `String` in `YYYY-MM-DD` form (produced by `getLagosBusinessDate()`), never as a `Date`, so they cannot shift by a timezone conversion.        |
| Table names        | `snake_case` via `@@map`.                                                                                                                                                         |
| Column names       | **camelCase** — Prisma maps table names only. Raw SQL must double-quote them (`"paidKobo"`).                                                                                      |
| Ledgers            | Append-only. A correction is a **new** row whose `reversesEntryId` points at the original.                                                                                        |
| Connection strings | Migrations/schema commands use `DIRECT_URL` (direct Neon host, no pooler) declared in `prisma.config.ts`. **The API process also uses `DIRECT_URL`**, with a small pool (`DB_POOL_MAX`, max 10): the pooled endpoint dropped connections during long transactional work, and a sale is one interactive transaction with `FOR UPDATE` row locks. Revisit at deployment. Tests use `TEST_DATABASE_URL` (direct; a `-pooler` host is refused). `DATABASE_URL` (pooled) is optional and unused by the API for now. |

## 4. Constraints in plain English

### 4.1 Signed ledger amounts (`20261017000100`)

No ledger amount may be zero, and each entry type carries a fixed sign:

- **Customer ledger** — `SALE` positive; `PAYMENT`, `RETURN`, `CUSTOMER_REFUND` negative; `ADJUSTMENT` either sign.
- **Supplier ledger** — `PURCHASE` positive; `PAYMENT` negative; `ADJUSTMENT` either sign.
- **Account ledger** — `SALE_PAYMENT`, `CUSTOMER_PAYMENT`, `TRANSFER_IN`, `OWNER_CAPITAL`, `OTHER_INCOME`, `OPENING_BALANCE`, `LOAN_DISBURSEMENT` positive; `SUPPLIER_PAYMENT`, `PURCHASE_PAYMENT`, `EXPENSE`, `CUSTOMER_REFUND`, `TRANSFER_OUT`, `OWNER_DRAWING`, `BANK_OR_POS_CHARGE`, `LOAN_REPAYMENT` negative; `ADJUSTMENT` either sign.
- **Loan ledger** — `DISBURSEMENT`, `CHARGE` positive; `REPAYMENT` negative.

#### Which amount is written (`recordSale` / `receivePurchase` / the payment services)

The sign above says which way the balance moves. This says which figure goes in
the row, and it differs between the two sides — so a ledger sum means the same
thing on both:

| Event | Row written | Amount |
| --- | --- | --- |
| Customer buys on credit (`recordSale`) | `customer_ledger_entries` `SALE` | **the unpaid portion only** — `totalKobo − paidKobo` |
| Customer pays the full total at the till | *no customer ledger row at all* | a fully paid sale is not a debt, so nothing is recorded |
| Customer pays later, on account | `customer_ledger_entries` `PAYMENT` | negative, the amount received |
| Supplier delivers (`receivePurchase`) | `supplier_ledger_entries` `PURCHASE` | **the full total**, `totalKobo` |
| We pay the supplier | `supplier_ledger_entries` `PAYMENT` | negative, the amount paid |

So `Σ(customer ledger) = what the customer owes` and
`Σ(supplier ledger) = what we owe the supplier`, in both cases positive when
money is owed. A debt payment deliberately does **not** set `saleId` on its
ledger row: the partial unique index `ux_customer_ledger_sale_active` allows only
one live entry per sale, and the original `SALE` entry already holds it.

#### Reversal rows are exempt from their own sign rule

A reversal must negate its target, so a reversal of a positive `SALE` entry is
itself negative — which the sign rule above would reject. Migration
`20261017070000` rebuilt the 4 ledger sign `CHECK`s (and
`ck_stock_movement_quantity_sign`) in the form

```sql
"reversesEntryId" IS NOT NULL OR (<the sign rule>)
```

and paired the exemption with `trg_*_reversal_integrity`, so the exemption
cannot be used to smuggle in an arbitrary row: once `reversesEntryId` is set,
the trigger re-reads the target and requires the new row to be identical to it
except for the magnitude column (`amountKobo`, or `quantityUnits` for
`stock_movements`), which must be its exact negation.

### 4.2 Stock movements (`20261017000200`)

- Exactly one of `purchaseLineId`, `saleLineId`, `transferLegId`, `adjustmentLineId`, `returnLineId` is set.
- `PURCHASE` positive, `SALE` negative, `RETURN` positive; `ADJUSTMENT` and `TRANSFER` non-zero in either direction (a transfer's sign is checked against its leg by a trigger).
- `unitCostKobo >= 0`.

### 4.3 Partial unique indexes (`20261017000300`)

- `products.sku` is unique **among non-deleted rows** only, so a deleted SKU can be reused.
- For each ledger, at most **one live entry** (`reversesEntryId IS NULL`) exists per source document — one entry per sale, sale payment, purchase, supplier payment, expense, transfer, etc.
- A given row can be the target of **at most one reversal** (`ux_*_reversed_once`): you cannot reverse the same entry twice.
- Account-ledger additions: one active purchase/loan/loan-repayment entry per source, one active opening balance per account, and one active entry per transfer direction (`ux_account_ledger_purchase_active`, `ux_account_ledger_loan_active`, `ux_account_ledger_loan_repayment_active`, `ux_account_ledger_opening_balance_active`, `ux_account_ledger_transfer_type_active`).

### 4.4 Value sanity (`20261017000500`)

- **products** — `unitsPerPack > 0`, all prices and the average cost `>= 0`, `reorderLevelUnits >= 0`, and a `sku` is stored upper-cased and trimmed.
- **customers** — `creditLimitKobo >= 0`.
- **purchases** — `totalKobo >= 0`, `paidKobo >= 0`, `paidKobo <= totalKobo`, `dueDate` matches `YYYY-MM-DD`.
- **purchase_lines** — `quantity > 0`, `unitsPerPackSnapshot > 0`, `quantityUnits > 0`, `PACK` lines have `quantityUnits = quantity * unitsPerPackSnapshot` and `UNIT` lines have `quantityUnits = quantity`, all money `>= 0`.
- **sales** — `totalKobo >= 0`, `paidKobo >= 0`, `paidKobo <= totalKobo`, and `channel <> 'BOTH'` (a sale is RETAIL or WHOLESALE; only a _product_ may be BOTH).
- **sale_lines** — as purchase lines, plus `unitPriceKobo`, `costPerUnitKobo`, `lineTotalKobo >= 0`.
- **stock_transfers** — `from <> to`; **stock_transfer_lines** — `quantityUnits > 0`.
- **stock_adjustment_lines** — `quantityDeltaUnits <> 0`, `unitCostKobo >= 0`.
- **sale_payments / supplier_payments** — `amountKobo > 0`.
- **expenses** — `amountKobo > 0`.
- **loans** — `principalKobo > 0`, `agreedInterestKobo >= 0`, `dueDate` matches `YYYY-MM-DD`.
- **loan_repayments** — `amountKobo > 0`, `interestPortionKobo >= 0`, `interestPortionKobo <= amountKobo`.
- **cash_snapshots** — `amountKobo >= 0`, `asOfDate` matches `YYYY-MM-DD`.
- **account/payment** (`20261019000100`) — `sale_payments.accountId` and `supplier_payments.accountId` are `NOT NULL`; deactivation-state columns must agree.
- **account_transfers** (`20261019000100`) — amount is positive and source/destination accounts differ.
- **account_balances** (`20261019000100`) — cached balance is non-negative; the ledger trigger is the only writer.
- **account_ledger_entries** (`20261019000100`) — at most one source column; a source-type trigger requires the appropriate source for sourced types and prohibits sources for manual types. `OPENING_BALANCE` must be positive; `ADJUSTMENT`, `OWNER_DRAWING` and `BANK_OR_POS_CHARGE` require a nonblank note.
- **expenses** (`20261019000100`) — `voidedAt` and nonblank `voidReason` must either both be set or both be absent.

### 4.5 Accounting links (`20261017000600`, `20261017060000`)

- The link between a loan repayment and the interest expense it generated is
  **one-directional**: `expenses.loanRepaymentId` (unique) references
  `loan_repayments.id` through `fk_expenses_loan_repayment`, which is
  **`DEFERRABLE INITIALLY DEFERRED`** and **`ON DELETE RESTRICT`** so a
  repayment cannot be deleted while an expense points at it. A repayment's
  expense is _derived_ by matching `loanRepaymentId` — `LoanRepayment` has no
  `expenseId` column (`20261017060000` dropped it along with its FK and index).
- **Write order** — inside one transaction: **(1)** the `loan_repayments` row,
  **(2)** its `loan_ledger_entries` REPAYMENT row, **(3)** the
  `LOAN_INTEREST` `expenses` row that points back at the repayment. Because the
  remaining FK runs expense → repayment, the ordering is natural and the
  `DEFERRABLE` clause is now belt-and-braces rather than a requirement.
- An expense that carries a `loanRepaymentId` **must** use category `LOAN_INTEREST`. The reverse is allowed: a manual `LOAN_INTEREST` expense may exist with no repayment.
- A `REPAYMENT` loan ledger entry **must** reference its `loanRepaymentId`; `DISBURSEMENT` and `CHARGE` entries **must not**.

### 4.6 Credit rules and the sale lifecycle (`20261017000700`)

- **Unpaid purchase requires a supplier** — if `paidKobo < totalKobo` then `supplierId IS NOT NULL`. Mirrors `createPurchase()`. A fully paid purchase (or a draft) needs no supplier.
- **Unpaid sale requires a customer** — if `paidKobo < totalKobo` then `customerId IS NOT NULL`. Mirrors `validateCompletedSalePayment()` and the UI, which refuses "a walk-in cannot owe money". `customerName` is deliberately **not** accepted as an alternative.
- **Sale status lifecycle** — `VOIDED` is terminal (no transition out of it) and a `COMPLETED` sale may never return to `DRAFT`. Legal transitions: `DRAFT → COMPLETED`, and any state `→ VOIDED`.

### 4.7 References

`sales.reference`, `purchases.reference` and `stock_transfers.reference` are unique. The columns are nullable, so **multiple NULLs are allowed** (Postgres treats NULLs as distinct in a unique index); a non-null reference can never be reused.

### 4.8 Admin users (`20261017051123`)

- **`email` is stored normalised** — `CHECK (email = lower(btrim(email)))`. The seed script normalises before writing; this CHECK is what enforces it against any writer.
- **`role` is not a security boundary.** `AdminRole` is `OWNER` or `STAFF` (default `STAFF`) and **nothing reads it yet** — there is no authorization layer, so every account has full access.
- **Accounts are deactivated, never deleted** (`isActive = false`): `purchases`, `sales`, `stock_transfers` and `stock_adjustments` reference `admin_users` with `ON DELETE RESTRICT`.
- **`lastLoginAt`** is nullable and stays null until sign-in exists. It is stored as `TIMESTAMPTZ(3)` (the documented convention above); note it is currently the only `timestamptz` column — every other timestamp column in the schema is `timestamp(3)`.

## 6. Database-enforced vs service-owned

**Enforced by the database (cannot be bypassed by application code):**

- Immutability of the 10 ledger/payment/audit tables (including `TRUNCATE`).
- Reverse-once and no-reversal-of-a-reversal.
- Account balances equal the sum of account-ledger entries and cannot go below zero; transfer pairs, source uniqueness, account deactivation, and the loan-interest no-double-outflow guard are enforced by constraints/triggers.
- Signed amounts for every ledger.
- Single-source stock movements, quantity signs, transfer-leg sign agreement.
- Every value-sanity rule in §4.4.
- Every foreign key, and `ON DELETE RESTRICT` on all of them (a referenced product, customer, supplier or sale cannot be hard-deleted).
- Every foreign key's **update** action is `ON UPDATE CASCADE` with **two deliberate exceptions that use `ON UPDATE NO ACTION`**: `fk_stock_balances_product` (`20261017100000_stock_balances`) and `account_balances_accountId_fkey` (`20261019000100_account_ledger_sources`). Both are hand-written constraints that declare only `ON DELETE RESTRICT`, which _is_ `NO ACTION` on update; `schema.prisma` mirrors that with `onUpdate: NoAction` so `prisma migrate diff` reports **no difference**. `NO ACTION` is safe here because a primary key is never updated — the referenced column is an immutable `cuid`/id. Declaring Prisma's default (`Cascade`) on either relation would make `prisma migrate dev` emit a migration that rewrites the constraint, so do not "tidy" them.
- Unique references and the active-SKU rule.
- Unpaid purchase requires a supplier; unpaid sale requires a customer.
- `VOIDED` is terminal for a sale; `COMPLETED` never returns to `DRAFT`.
- Expense ↔ loan-repayment links and loan-ledger source exclusivity.
- `admin_users.email` is stored lower-cased and trimmed (`20261017051123`).
- **Stock never goes below zero**, per `(product, location)`, and there is at most one balance row per pair (`stock_balances`, `ck_stock_balances_nonnegative`, `20261017100000`). The balance is a row-locked cache, so two concurrent sales of the last unit cannot both succeed — one fails the `CHECK`.
- **Account money never goes below zero** (`account_balances`, `ck_account_balances_nonnegative`, `20261019000100`). A row-locked balance cache is updated from immutable account-ledger inserts; direct writes are rejected.
- **A reversal must be the exact negation of its target** and match it on `type` and every source column (`trg_*_reversal_integrity`, `20261017070000`).
- **Expense immutability** — a `LOAN_INTEREST` expense is fully immutable, and `category` + `loanRepaymentId` are immutable on every expense (`20261017090000`).
- **A sale with on-account payments cannot be voided** (`trg_sale_void_guard`, `20261017092000`) — voiding would strand the customer ledger `PAYMENT` entry.
- **Document locks** — past `DRAFT`, only `paidKobo`, `status` and `updatedAt` may change, a non-draft document cannot be deleted, and the sale/purchase/transfer/adjustment line tables are immutable (`20261017110000`).

**Owned by the service layer (the database cannot express these):**

| Rule                                                         | Why it is service-owned                                                                                                                                                                    |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Insufficient-stock messages                                  | The database refuses the oversell (`ck_stock_balances_nonnegative`); turning that failure into a friendly "only 3 left" message, and checking before attempting the write, is the service's job (`apps/api/src/modules/stock/stock.service.ts`). |
| `lineTotalKobo` equals unit cost × quantity                  | Legitimate rounding can differ; the service computes the line total once and stores it.                                                                                                    |
| `paidKobo` equals the sum of the matching payment rows       | `paidKobo` is a denormalisation the payment service owns; `pnpm --filter @fabtyna/api db:audit` (§7) proves there is no gap.                                                                |
| A `PURCHASE`/`SALE` line quantity must result in whole units | Arithmetic and pack snapshots are resolved before the insert. A fractional `PACK` quantity (½ crate) is accepted, but only when it resolves to a whole number of base units — the check is done in scaled integers in `receivePurchase`/`recordSale`. |
| VOIDED sales/purchases/transfers must not be edited          | Immutability plus the status triggers cover most of it; the remaining "don't offer the action in the UI" checks live in the app.                                                           |
| Debtor aging / payment allocation to the oldest unpaid sale  | Computed at query time; there is no allocation table.                                                                                                                                      |
| Sale payment amount ≤ amount due; `paidAt`/`soldAt` not in the future | The domain checks the amount; the future-date limit (5 min tolerance) and "sale is COMPLETED" are checked in `sales.service.ts` under the sale row lock. |
| Void refused for already-voided sales and for later (on-account) payments; friendly overdraw message | `trg_sale_void_guard` and `ck_account_balances_nonnegative` are the backstops; the service checks first, under the lock order sale → products → stock_balances → account_balances → customer, to return a friendly 409. |
| Amend = void + new sale in one transaction                   | Pure service orchestration; the link is audit metadata (`amendedBySaleId` / `amendedFromSaleId`), no schema change.                                                                        |
| Purchase void refused when a LIVE supplier payment exists    | `trg_purchase_void_guard` (`20261020000400`) is the backstop; the service checks first under the purchase row lock and returns a friendly 409 ("Reverse the payments first").            |
| Payment reversal (sale later payments, any supplier payment) | Service-owned rules (walk-in sale refused, up-front payment refused, reason required, overdraw message); once-only is `ux_*_reversed_once`; reversal integrity is `fn_check_reversal_integrity`. |
| Purchase void refused when its stock was already sold; friendly overspend/overdraw messages | `ck_stock_balances_nonnegative` and `ck_account_balances_nonnegative` are the backstops; the service checks first, under the lock order purchase → products → stock_balances (all locations) → account_balances → supplier (`FOR SHARE`). |
| Purchase `averageCostKobo` is recomputed on receive and void | Done by the shared domain, never by SQL; two purchases of one product serialise through the product row so the average is never computed from stale stock. |
| Amend purchase = void + new purchase in one transaction      | Service orchestration; link in audit metadata (`amendedFromPurchaseId` / `amendedByPurchaseId`), no schema change. |

## 7. Drift audit

Denormalised columns (`totalKobo`, `paidKobo`, `stock_balances.quantityUnits`)
can drift from the immutable rows they are derived from, because the database
cannot express "equals the sum of another table" as a constraint — Postgres
`CHECK` constraints cannot contain a subquery. `db:audit` is the read-only
counterpart of `db:verify`: `verify` proves the *rules* are installed, `audit`
proves the *data* obeys them.

```bash
pnpm --filter @fabtyna/api db:audit
pnpm --filter @fabtyna/api db:audit -- --url TEST_DATABASE_URL
```

It runs every query below, prints the offending rows, and **exits non-zero if
any of them return a row**. All of them must return zero rows on clean data.

| Check | Query shape |
| --- | --- |
| `purchases.totalKobo` = Σ `purchase_lines.lineTotalKobo` | group each purchase's lines and compare to the header |
| `sales.totalKobo` = Σ `sale_lines.lineTotalKobo` | as above, on the sale side |
| `purchases.paidKobo` = Σ `supplier_payments.amountKobo` | left join, `COALESCE(..., 0)` |
| `sales.paidKobo` = Σ `sale_payments.amountKobo` | as above, on the sale side |
| Customer ledger balance = Σ unpaid portions | per customer, `Σ(customer_ledger_entries.amountKobo)` vs `Σ(totalKobo − paidKobo)` over non-`VOIDED` sales |
| Supplier ledger balance = Σ unpaid portions | per supplier, `Σ(supplier_ledger_entries.amountKobo)` vs `Σ(totalKobo − paidKobo)` over non-`VOIDED` purchases |
| `stock_balances` = the movement sum | left join every `(productId, location)` in either table and compare `quantityUnits` |
| `account_balances.balanceKobo` = Σ `account_ledger_entries.amountKobo` | compare each cached balance with the ledger sum |
| Exactly one original entry per sale payment, supplier payment, non-`LOAN_INTEREST` expense, loan disbursement and loan repayment | source document left-joined to non-reversal account entries |
| Exactly one `PURCHASE_PAYMENT` per paid supplier-less purchase | paid supplier-less purchase left-joined to its non-reversal account entry |
| Reversals net to zero | sale/supplier payment and expense checks plus purchase, loan and transfer reversal totals |
| One original IN and OUT entry per transfer | account transfer joined to its live ledger entries |
| Account source cardinality | source-backed types carry one source column; opening balance, adjustment, owner capital/drawing and bank/POS charge carry none |
| No account entry for a `LOAN_INTEREST` expense | expense category joined to account-ledger entries |
| Deactivated accounts have no original entries | account entries joined to inactive accounts; reversals are permitted |

The first four queries were previously only a comment at the bottom of
`20261017000500_value_checks`; the script now runs them for real.

> Known exceptions — deliberate, not drift:
>
> - A purchase with **no supplier** records no `supplier_payments` row at all
>   (`SupplierPayment.supplierId` is NOT NULL), so a paid supplier-less purchase
>   appears in the `purchases.paidKobo` check. The domain layer still sets
>   `Purchase.paidKobo`. The script reports these as a separate, non-fatal
>   `known` bucket rather than a failure.
> - A voided document legitimately keeps its lines and its `totalKobo`, so the
>   two total-vs-lines checks include `VOIDED` rows; the ledger checks do not
>   (a voided sale/purchase is excluded from the "what is owed" comparison,
>   because voiding writes a reversing ledger entry rather than deleting the
>   original).
> - Source-less `OPENING_BALANCE`, `ADJUSTMENT`, `OWNER_CAPITAL`,
>   `OWNER_DRAWING` and `BANK_OR_POS_CHARGE` account entries are intentional;
>   the source-cardinality audit permits those exact types and requires one
>   source column for all source-backed types.
> - `LOAN_INTEREST` expenses intentionally have no account entry. The full
>   repayment amount, including interest, is the single `LOAN_REPAYMENT`
>   outflow.

## 8. Trigger behaviour fixes (`20261017120000`, `20261017130000`)

`db:verify` proves that a trigger *exists*; it does not look inside the
PL/pgSQL body, so a trigger can be present, pass `verify`, and still never fire
or always fire. Three defects shipped that way in `20261017100000` /
`20261017110000` and were corrected by `20261017120000`. Each is a PL/pgSQL
trap worth remembering:

| Defect | Symptom | Cause | Fix |
| --- | --- | --- | --- |
| `fn_check_document_lock` compared a `SaleStatus`/`PurchaseStatus` (enum) column to a `TEXT` local | `42883 operator does not exist` on **every** sales/purchases `UPDATE`/`DELETE` | PL/pgSQL does not implicitly cast enum ↔ `text` in a comparison | compare `jsonb` images: `(to_jsonb(OLD) ->> 'status') IS DISTINCT FROM 'DRAFT'` |
| `fn_check_reversal_integrity` tested `IF NOT FOUND` after `EXECUTE ... INTO` | **every** reversal was rejected | `FOUND` is set by `SELECT INTO`/DML, **not** by `EXECUTE ... INTO` | fetch `to_jsonb(t)` into a `JSONB` variable and null-check that instead |
| `fn_stock_balance_direct_write_guard` used `pg_trigger_depth() = 0`; the maintainer returned a bare `RETURN NULL` | the guard never rejected anything, and a `BEFORE` guard's `RETURN NULL` silently cancelled the write | inside a trigger `pg_trigger_depth()` is always ≥ 1, so `= 0` is unreachable; `RETURN NULL` from a `BEFORE` row trigger skips the operation instead of raising | guard on `pg_trigger_depth() <= 1 → RAISE`, and `RETURN NEW`/`RETURN OLD` on the pass-through path |

`20261017130000` fixes a fourth, non-trigger issue in the same area:

| Defect | Symptom | Cause | Fix |
| --- | --- | --- | --- |
| `fn_apply_stock_movement` used `INSERT ... ON CONFLICT DO UPDATE` | `23514 ck_stock_balances_nonnegative` on legal negative movements | Postgres evaluates `CHECK` constraints on the **proposed** row *before* `ON CONFLICT` arbitration, so the intermediate `(0 − n)` value was rejected even when the final merged value was positive | an UPDATE-first loop (update the existing row, insert only if no row was found, retry on `unique_violation`) so the `CHECK` always sees the merged value |
| The account-balance maintainer could have the same `INSERT ... ON CONFLICT` defect | a legal first outflow against an already-positive account balance could be rejected | The proposed insert delta is negative and violates the CHECK before conflict resolution can merge it with the positive balance | `fn_apply_account_ledger_entry` uses UPDATE-first, inserts only when the account has no balance row, and retries the UPDATE after a concurrent first insert; the UPDATE holds the row lock so concurrent spends serialize |
| The account-balance direct-write guard copied the stock guard's pre-fix logic | every account-ledger entry was accepted without updating `account_balances`; the non-negative CHECK never protected the money | Inside a row trigger, `pg_trigger_depth()` is 1 for direct writes and 2 for the maintainer's nested write, so `= 0` is unreachable; `RETURN NULL` silently cancels both direct writes and the maintainer's writes | `20261019000300` raises when depth is `<= 1` and returns `NEW`/`OLD` on the allowed nested path. The migration reconciles cached rows from immutable ledger entries. |

Both migrations also re-backfill `stock_balances` from `stock_movements` and are
proven by the API test suite (`stock-balances.test.ts`,
`reversal-positive.test.ts`), not just by `db:verify`.
